# 性能基线与使用边界

M6 保留整包重写，不新增增量容器或存储抽象。以下数据用于定位规模成本，不是跨机器性能保证，也不代表已验证所有默认上限。

## 复现

```bash
npm run bench
npm run bench -- --quick
```

完整集为 10/100/1000 个历史版本 × 每版 2/64 KiB，Ref/Doc 各占一半，Document 绑定最新 Ref；两个工作副本与各自 HEAD 相同。使用 STORE、确定大小的文本与有效 hash。数据是合成历史，不是用户文档语料；它适合测量条目与总字节成本，不能代表压缩、图片解码或真实渲染性能。

每个场景独立进程，建包在父进程，不计入时延或子进程峰值 RSS。按顺序测 open、读取最旧 Document 正文、trace、full verify、save、commit，共三轮并记录全部样本和中位数；每轮 commit 追加一个真实版本，初始 N 轮次依次为 N/N+1/N+2。系统缓存没有清空，首次样本也保留；结果偏向本地 warm-cache 使用。`peakRssKiB` 是整个测量进程的峰值，包含 V8 和所有操作，不是单操作分配量或泄漏结论。

CI 仅在 Linux / Node 24 运行 `--quick` 验证基准脚本仍可执行，[`52f1d33` 的 CI](https://github.com/owariband/mdv/actions/runs/34193879318) 已通过该步骤，不以共享 runner 的毫秒数设硬阈值。机器、磁盘、Node、文件系统、后台负载不同，应重新测量。

## 2026-09-08 本地结果

macOS Darwin 25.4.0 / arm64 / Apple M5 Pro / Node 26.3.0。原始环境、全部三轮时延和峰值见 [JSON 基线](../bench/baselines/2026-09-08-darwin-arm64-node26.json)。表中耗时单位为 ms，RSS 单位为 MiB（原始 KiB ÷ 1024）。

| 10 | 2 KiB | 1.5 | 0.8 | 1.9 | 21.4 | 21.0 | 75.7 |
| 10 | 64 KiB | 1.7 | 0.7 | 2.2 | 22.7 | 24.0 | 92.0 |
| 100 | 2 KiB | 11.0 | 4.0 | 11.2 | 64.6 | 59.9 | 106.7 |

最大场景 ZIP 约 63.3 MiB，trace 中位数约 0.12 ms。读取历史只解压被选择的正文，但当前路径 Reader 仍需重新索引 ZIP，所以单次读取不应被描述为常数成本的随机访问。

## 当前结论

本机数据没有提出必须改变 Format 0.1 的证据。整包重写成本随历史条目和总字节上升；尤其 1000 × 64 KiB 的 save/commit 已各约 0.65 秒，因此适合作为显式保存/提交，不适合宿主每次按键立即调用 save。编辑器应保留内存 buffer，按需合并保存请求，并串行消费 Core 返回的新 generation；不能通过并发排队旧 generation 来模拟自动合并。

默认 10,000 Version / 512 MiB 是防御性预算，不是“该规模也能流畅编辑”的承诺。尚未实测该上限，也未完成 Windows/Linux 的六场景性能基线、长时间循环、真正断电或低内存设备测试；Linux CI 的 smoke 不代替这些验证。正式发布前应结合目标宿主预算补测。后续只有真实接入数据表明不可接受时，才讨论索引/扫描优化或下一格式的增量结构。
